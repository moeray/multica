Connect a Multica agent as a Feishu Bot and team members can DM it in Feishu, @-mention it in a group, or use `/issue` to create issues. Conversations and run records are still saved to the Multica workspace.

Each Bot maps to exactly one agent. To use several agents in Feishu, connect a Bot for each of them.

## Connect a Bot

The agent's owner and workspace owners and admins can start a connection:

1. Open **Agents** and select the agent to connect to Feishu.
2. Go to **Integrations** and click **Bind to Feishu**.
3. Scan the QR code with Feishu and confirm the authorization.
4. Return to Multica. Once the page shows **Connected to Feishu**, the Bot is ready.


The QR code is a one-time credential; if it expires, generate a new one. An agent that is already connected no longer shows the scan entry point; to rename the Bot or adjust its permissions, click **Manage in Feishu**.

<Callout type="info">
New connections are currently open only for mainland-China Feishu. Existing international Lark connections keep working and can still be managed.
</Callout>

## First use

The first time a member messages the Bot, they receive an account binding link:

1. Open the link and sign in to Multica.
2. Confirm the workspace account to link.
3. Return to Feishu and send the message again.

Only after binding can Multica confirm which workspace member a message comes from. Non-members cannot use the Bot.

## Hand work to the agent in Feishu

### Direct messages

Message the Bot directly. Consecutive messages stay in the same Multica conversation, and the agent's replies go back to that conversation.

### Group chats

Add the Bot to the group first, then `@Bot` and describe what you need. The Bot only responds to messages that explicitly @-mention it; when it runs, it draws on the recent context it can read in the current session.

### Create an issue

Send:

```text
/issue Fix the redirect after login
Safari stays on the login page after a successful sign-in.
```

The first line becomes the title and the rest becomes the description. Sending `/issue` alone creates nothing; the Bot replies with the required format instead.

## Manage connections

Open **Settings → Messaging → Lark** to view the Bots connected in the workspace. Workspace owners and admins can disconnect them here; an agent's owner can also manage their own Bot from that agent's **Integrations** page.

After disconnecting, the Bot stops receiving new messages. Existing conversations and audit records are not deleted.

## Inbox notifications

Inbox notifications use a destination each member chooses explicitly. The destination is a Feishu bot plus that member's Lark identity, and it does not change when the item comes from a different agent, an autopilot, or another member.

1. Open the **Inbox** page menu and choose **Feishu notifications**.
2. Pick an agent Bot you have already bound in Feishu, or install a dedicated inbox Bot. A dedicated Bot is not attached to an agent.
3. Select a destination and save. Use **Send test** to confirm the Bot can reach you.

Notifications from every source now go through that one destination. If no destination is configured, or it is disabled, items stay in the Multica inbox and nothing is sent. Multica does not fall back to the most recently bound Bot.

Each inbox item creates a durable delivery record. Failed sends retry with bounded backoff and can be retried manually from the same dialog; pending work resumes after a restart, and multiple server replicas cannot consume the same record twice. Delivery failures never remove the inbox item or block the task or issue request that created it.

Replacing or unbinding a destination cancels queued deliveries for the old target. A send that was already in flight when the target changed may still arrive, and a timeout after Feishu accepted a message can produce a duplicate: delivery evidence exposes those states, but Multica does not promise end-to-end exactly-once delivery.

Existing Feishu bindings are not used to infer a destination during migration. Every member must make an explicit choice the first time they enable external inbox notifications. To roll back, disable the destination; the in-app inbox continues to work. The database rollback drops the destination and delivery outbox tables and the dedicated Bot rows.

## Self-hosting setup

Multica Cloud needs no extra configuration. A self-hosted deployment must first set a key used to encrypt Bot credentials:

```dotenv
MULTICA_LARK_SECRET_KEY=<base64-encoded 32-byte key>
```

Generate one like this:

```bash
openssl rand -base64 32
```

Restart the API server, then connect the Bot from the agent's **Integrations** page. Keep this key long-term: if it is rotated or lost, existing credentials can no longer be decrypted and the Bot must be reconnected.

`MULTICA_LARK_HTTP_BASE_URL` and `MULTICA_LARK_CALLBACK_BASE_URL` exist only for special deployments such as proxies and testing; leave them unset in normal operation.

## Troubleshooting

- **No bind button**: confirm the current account is the agent's owner or a workspace owner or admin, and check that the self-hosting key is configured.
- **QR code expired**: close the dialog and start the connection again.
- **The Bot asks for account binding**: open the binding link and sign in with the Multica account for that workspace.
- **Feishu inbox notifications never arrive**: open the Inbox page menu, confirm the destination is active, and use **Send test**. The same dialog lists recent delivery attempts and their last error. With no destination, items intentionally stay in Multica only.
- **A notification went to the wrong bot**: replace the destination explicitly. Queued deliveries for the old target are cancelled; in-flight requests already accepted by Feishu may still arrive.
- **The Bot doesn't run**: check whether the agent is archived and whether the [runtime](/daemon-runtimes) it uses is online.
- **The Bot never replies at all**: the app must push events over a long connection — Multica has no webhook endpoint. In the Feishu/Lark developer console, open **Events & Callbacks → Event Configuration** and confirm that the subscription method is the long connection rather than a request URL, that `im.message.receive_v1` is subscribed, and that the app version carrying that configuration is published (and approved, where the tenant reviews releases). An app set to a request URL still binds, still shows Connected, and silently receives nothing.
